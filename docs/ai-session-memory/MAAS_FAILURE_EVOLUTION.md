# MAAS Failure Evolution

Updated: 2026-07-07

Purpose: keep the MAAS loop from repeating the same visual and research-method failures. This file is part of the current memory contract; read it before changing mass language, source geometry, selection, verifier gates, or presentation artifacts.

## Ground Rules

- Legal constraints are hard gates. LLM output may propose language and parameters, but FAR/BCR/height/envelope/parking checks must be deterministic evidence.
- Parking count and mass-stage parking are not the same as permit-final parking. Do not claim permit-final parking pass unless `parking_permit_pass` is true.
- Architectural diversity is not volume count, family count, or random role count. It needs a legible dominant gesture, hierarchy, alignment, and describable composition rule.
- Clean-room paper adaptation must be labeled as such. Current MAAS follows paper-inspired harness ideas, not an exact reproduction of EvoMass, CAD-Assistant, or other cloned repositories.

- too many candidates contain small helper fragments,
- language mixing is unclear.

## Current Architecture-Grade Goal

The next target is not merely cleaner boxes. The final 20-card sheet should
contain strong geometric massing principles from user-provided books/references
and precedent buildings:

- slender tower/podium order,
- undercut or carved base where parking/ground logic allows,
- tapered or twisted tower silhouette,
- stacked and shifted platform logic,
- folded/sloped roof volume,
- carved atrium or courtyard void,
- split/bridge connector with a readable main/support hierarchy.

These are design ambitions. Legal and parking gates remain deterministic.

## Implementation Principle

When a future loop needs “more diverse massing,” do not first add more source volumes. Prefer this order:

1. Add or refine architectural grammar language.
2. Make the language compile into source geometry with a dominant gesture.
3. Check legal envelope and parking count/mass-stage.
4. Measure repair delta.
5. Measure orderliness.
6. Render PNG and visually inspect.
7. Only then update memory and presentation artifacts.

## Required v19 Direction: LLM-In-The-Loop Is The Main MAAS Structure

- Clarification from user: the main research/system structure is not merely a
  deterministic grammar generator. The intended MAAS pipeline must be:
  `LLM/agent architectural language proposal -> MassDSL contract -> source
  geometry compiler -> legal envelope / parking verifier -> review PNG`.
- The recent `MAAS_LLM_LOOP_REQUIRED=0` renders were stabilization and
  debugging runs only. They prove the deterministic compiler/legal/parking
  harness can keep proposals legal and readable, but they are not the final
  target architecture.
- Current LLM-off output still uses saved agent-authored proposal artifacts
  such as `agent_oma_diagonal_plate`, `agent_vancouver_torque_stack`, and
  `agent_big_terrace_cascade`; however, it does not generate fresh OpenAI LLM
  candidates during render time. That is why the JSON verifier still reports
  LLM evidence failures.
- Next implementation target:
  - run the MAAS render with `MAAS_LLM_LOOP_REQUIRED=1`,
  - ensure the LLM proposal loop emits schema-valid MassDSL batches,
  - keep legal/parking gates mandatory,
  - require enough final direct LLM candidates in the 20-card set,
  - compare LLM-authored candidates against deterministic/agent proposal
    baselines by PNG and JSON verifier.
- Do not treat LLM as decorative text. It must author or select architectural
  language combinations and numeric MassDSL parameters; deterministic code must
  compile, clip, score, and reject them against law/parking constraints.
