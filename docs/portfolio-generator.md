# Portfolio Generator

프로젝트가 많아서 만들었다. 하나씩 수동으로 포트폴리오 만들 시간이 없기 때문에, **Claude Code + 나노바나나 2**로 자동화한다.

---

## 왜 이걸 만들었는가

### 문제
- 프로젝트 10개 넘게 쌓여 있는데 포트폴리오에 정리된 건 없음
- 매번 처음부터 구조 잡고, 스크린샷 찍고, 다이어그램 그리면 **프로젝트당 하루**
- 면접에서 "이 프로젝트 아키텍처가?" 물어보면 코드 뒤져야 함
- 이미지는 Figma로 일일이 만들거나 스톡 이미지 쓰면 일관성 없음

### 해결
- Claude Code가 코드베이스를 읽고 **8개 섹션 자동 생성** (5분)
- 나노바나나 2 (Gemini)가 **이미지 8장 자동 생성** (10분)
- 프로젝트당 **15분**이면 완성급 포트폴리오

### 워크플로우
```
① 프로젝트 폴더에서 Claude Code 실행
   ↓
② Claude가 README, package.json, git log, 폴더 구조 자동 분석
   ↓
③ docs/portfolio.md 생성 (8개 섹션 + 나노바나나 프롬프트 8개)
   ↓
④ 프롬프트를 Gemini에 복붙 → 이미지 8장 생성
   ↓
⑤ 포트폴리오 사이트에 적용
```

## 리서치 기반 — 뭘 넣어야 하는가

### 개발자 포트폴리오 필수 항목 (2026 업계 기준)

1. **Problem → Solution** — 왜 만들었는가. "기술 썼다"가 아니라 "이 문제를 이렇게 풀었다"
2. **Architecture Diagram** — 서비스 간 통신, 데이터 흐름. 면접에서 무조건 물어봄
3. **Tech Stack + 선택 이유** — React 쓴 이유, Django 쓴 이유. "유행이라서"는 탈락
4. **Troubleshooting** — 가장 중요. 에러 → 원인 분석 → 해결. 실력 증명의 핵심
5. **정량 지표** — "빠르다" 말고 "3초", "31,126 노드", "235 E2E 테스트"
6. **Live Demo** — 배포 URL 또는 GIF. 돌아가는 걸 보여줘야 함
7. **코드 접근** — GitHub 또는 핵심 코드 스니펫

### PM 포트폴리오 추가 항목
- WHY 1페이지 → HOW 2-3페이지 → WHAT 1페이지 (프로젝트당 5-6p)
- 의사결정 과정과 트레이드오프
- Before/After 정량 비교
- 프로젝트는 3개 정도가 적당

### 흔한 실수
- 기술 나열만 하고 왜 쓴지 안 씀
- 트러블슈팅 없음 (= 문제 해결 경험 증명 불가)
- "열심히 했다" 같은 주관적 표현 (숫자로 대체)
- 스크린샷만 있고 아키텍처 없음
- 배포 안 되어 있음

## 8개 섹션 상세 가이드

### 섹션 1: Problem & Solution

**목적**: 30초 안에 "이 프로젝트가 왜 존재하는지" 이해시키기

**작성법**:
```markdown
### 문제
[누가] [뭘 하려면] [이런 고통이 있다]
- 구체적 수치: "1건에 2~3시간", "법조문 200개 수동 검토"

### 해결
[한 문장]: "주소 하나 → 3초 → 42개 규제 자동 분석"
- Before/After 비교
```

**ACE 프로젝트 실제 예시**:
```markdown
### 문제
건축사가 토지 규제를 분석하려면:
- 국가법령정보센터에서 20개 법률 수동 검색
- 1건에 2~3시간, 법조문 200개 이상 검토

### 해결
주소 하나 입력 → 3초 만에 42개 규제 + 8종 규제선 + 170개 법조항 자동 분석
```

### 섹션 2: Architecture

**목적**: 시스템이 어떻게 생겼는지 한눈에 보여주기

**작성법**: ASCII 다이어그램 + 서비스 테이블

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│ Frontend │───>│  API     │───>│  DB      │
│ (React)  │    │ (Django) │    │ (Neo4j)  │
└──────────┘    └──────────┘    └──────────┘
```

**팁**:
- 서비스 간 화살표에 프로토콜 라벨 (REST, WebSocket, SSE)
- 각 서비스에 호스팅 플랫폼 표기 (CF Workers, Railway, Vercel)
- 포트 번호는 생략 (포트폴리오니까)

---

### 섹션 3: Tech Stack

**목적**: 기술 선택의 근거를 보여주기

**작성법**: 카테고리 × 기술명 × 버전 × 선택 이유

```markdown
| 기술 | 버전 | 선택 이유 |
|------|------|-----------|
| React | 19.2 | Concurrent Mode + Server Components |
| Django | 6.0 | 빠른 프로토타이핑, ORM 내장 |
```

**팁**:
- "선택 이유" 칸이 핵심. 면접에서 물어보는 게 이거
- 대안과 비교한 내용 있으면 더 좋음 ("Express 대비 Django는...")
- 버전 정확히 (package.json에서 추출)

---

### 섹션 4: Data Flow

**목적**: 입력부터 출력까지 단계별 흐름

**작성법**: 번호 매긴 단계 + 각 단계에서 어떤 기술이 동작하는지

```markdown
① 사용자 입력 → ② API 호출 → ③ 처리 → ④ 결과 반환 → ⑤ 시각화
```

**팁**: 7단계 이하로. 너무 많으면 읽기 힘듦.

---

### 섹션 5: Troubleshooting (가장 중요!)

**목적**: 문제 해결 능력 증명. 면접관이 가장 보고 싶어하는 섹션.

**작성법**:
```markdown
### [한 줄 제목]
**문제**: [에러 메시지 또는 증상]
**원인**: [분석 과정 — 로그, 디버깅]
**해결**: [구체적 코드/설정 변경 — 파일명 포함]
**교훈**: [재발 방지 또는 설계 원칙]
```

**ACE 프로젝트 실제 예시 4개**:

```markdown
### 1. 법제처 API 간헐적 다운 (522/525)
**문제**: law.go.kr API가 간헐적 다운 → 조문 조회 실패, 사용자에게 빈 결과
**원인**: 법제처 서버 Cloudflare origin 연결 실패 (과부하 또는 SSL 문제)
**해결**: 3중 fallback — ① Neo4j(로컬) → ② AG-light Worker(Vectorize) → ③ 법제처 API
**교훈**: 외부 API 의존 시 반드시 fallback 체인. 단일 장애점 제거

### 2. Vectorize ID ↔ Neo4j full_id 형식 불일치
**문제**: 조문 카드 클릭 시 `Get article failed: 400`
**원인**: Worker ID `건축법_제60조` vs Neo4j `건축법(법률)::제6장::제60조::1`
**해결**: `_article_by_vectorize_id()` 매핑 함수. JO.number="60조"(제 없음) + 법률>시행령>시행규칙 우선순위
**교훈**: 서로 다른 시스템 간 ID 형식은 설계 시 통일하거나 어댑터 필수

### 3. Vworld 3D basemap 변경 불가
**문제**: Vworld 3D SDK에 basemap 변경 API 없음 — 위성만 제공
**원인**: SDK가 Cesium을 래핑하지만 imagery provider 교체 인터페이스 미노출
**해결**: ws3dInitCallBack에서 Cesium imagery 직접 교체 — removeAll() + UrlTemplateImageryProvider(Base 타일)
**교훈**: SDK 제한 시 내부 엔진(Cesium) 직접 접근. 래퍼 뚫기

### 4. 일조사선 2023 개정 미반영
**문제**: 정북일조 계산이 구법(9m 기준)으로 동작
**원인**: 건축법 시행령 제86조 2023.9.12 개정 — 9m→10m 기준 변경
**해결**: setback_geometry.py에서 H≤10m→1.5m, H>10m→H×0.5. 전용/일반주거만 적용
**교훈**: 법률 기반 시스템은 개정 추적 필수. 하드코딩 값에 개정일 주석
```

### 섹션 6: Key Metrics

**목적**: 주관적 형용사 대신 숫자로 증명

**수집 방법** (Claude가 자동):
```bash
# 코드 라인 수
find . -name "*.py" -o -name "*.ts" -o -name "*.tsx" | xargs wc -l

# 테스트 수
grep -r "def test_\|it(" --include="*.py" --include="*.ts" | wc -l

# 파일 수
find src -name "*.tsx" | wc -l

# Git 커밋 수
git log --oneline | wc -l
```

**좋은 지표 예시**:
- 노드/레코드 수: "31,126 노드"
- 테스트: "235 E2E + 93 단위"
- 응답시간: "~3초 (전체 파이프라인)"
- 번들 크기: "242KB (gzip 47KB)"
- API 수: "57개 MCP 도구"
- 법률 커버리지: "20법 58법령"
